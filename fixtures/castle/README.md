# Castle SDK archive

Complete, captured copies of X's Castle.io SDK chunks
(`@castleio/castle-js`), served from `abs.twimg.com/x-web/x-web/assets/`.

## Why

`$castle_token` — generated by Castle's behavioral/device fingerprinting — is
required by X's `begin_login` endpoint. Castle's chunk filename *and* its
minified tamper-check shape both drift between builds (see
`src/runtime/webview/proxy.ts` → `CASTLE_BUILD_VERSIONS`). When X ships a new
build, we want the full copy of the previous ones on hand to diff against and
to extract the new tamper-check shape for a new registry entry.

These are reference copies only — nothing in the app imports them. They exist so
a "new Castle build" is a diff-able artifact, not a mystery.

## Adding a new build

```bash
node scripts/archive-castle.mjs castle.umd-<hash>.js
```

This fetches the chunk from `abs.twimg.com/x-web/x-web/assets/`, saves it here,
and reports whether its tamper-check shape matches any known registry entry.
Then:

1. Diff the new file against the previous one to locate the tamper-check
   functions (search for `try{return` / `catch{return!1}` patterns).
2. Add a `{ name, fingerprint, instrument }` entry to `CASTLE_BUILD_VERSIONS`.
3. Update the table above with the filename → entry mapping.
